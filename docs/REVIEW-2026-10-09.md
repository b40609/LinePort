# LinePort 程式檢查與優化建議（2026-10-09）

本次交付 v0.3.1，修復可重現的請求停滯及 Telegram 收件紀錄驗證問題。檢查不是完整滲透測試，也不能保證找出所有 Bug 或漏洞。

後續 v0.4.0 已完成待送佇列、公平排程、Telegram 限流等待、容量預警與設定衝突檢查，詳見 [實作範圍與限制](OPTIMIZATION-0.4.0.md)。下列建議保留為原始評估紀錄。

以下優先順序是依 LinePort 現況提出的設計建議，並非宣稱上述專案採用相同實作。

## 已修復

| 問題 | 原本影響 | 修正與驗證 |
| --- | --- | --- |
| 單一來源讀取一直未完成 | 整輪停在共同等待，健康來源也無法發送 | 多規則平台操作預設 30 秒期限；來源退避重試時沿用尚未完成的讀取，不產生重疊請求；測試確認恢復後仍能接續處理 |
| 目的發送一直未完成 | 整輪不再進入下一次輪詢 | 到期將該配對持久記為結果不明並暫停；即使晚到成功回應，重啟也不自動重送 |
| 目的準備／來源首次讀取一直未完成 | 其他獨立配對無法完成初始化 | 個別準備與基準讀取也有期限；新增獨立目的仍可啟動的測試 |
| Telegram 異常時間或 offset 溢位 | 無效資料先寫入 JSONL，重新啟動持續失敗；記憶體 offset 也可能先推進 | 寫檔與套用 offset 前均驗證資料；測試證明無效資料不污染紀錄、重啟後仍從原 offset 讀取 |

前兩個請求停滯案例與兩個 Telegram 異常資料案例，都先確認測試在舊實作失敗，再修正至通過。沒有刪除或修改使用者的既有收件紀錄。

## 建議優先順序

| 優先度 | 建議 | 完成標準 |
| --- | --- | --- |
| P1 | 各目的持久待送佇列、公平排程與限流 | 大量積壓不阻擋其他來源；僅對明確未發送的錯誤退避重試，發送不明維持人工核對 |
| P1 | 收件紀錄封存、磁碟配額、容量預警 | 接近 50,000 則前通知；經授權備份後整理，保留去重證據與未送資料 |
| P1 | Windows 使用者綁定的憑證加密 | Bot Token 與登入資料使用 DPAPI 等機制保護；先處理 Yomi 儲存介面及可回復的遷移 |
| P1 | 多分頁設定版本衝突檢查 | 舊頁面保存時提示重新載入，避免覆蓋另一頁剛修改的規則 |
| P2 | 圖片／檔案、來源名稱及回覆資訊 | 共用訊息模型、平台能力表、檔案大小與類型限制；不轉送平台保護內容 |
| P2 | 訊息 ID 對應、編輯及刪除同步 | 分開保存每個目的的回應 ID，提供明確可選的同步規則 |
| P2 | 發布版本 ZIP、校驗碼與更新提示 | 朋友可辨識版本、下載與回復；更新前停止背景服務 |
| P2 | Discord／Slack 等平台 adapter | 各自使用正式 API，補齊權限、限流與獨立整合測試；不直接承諾 LINE 社群可沿用一般群組協定 |

## 檢查與驗證範圍

- 現行 `yomi-probe/`：HTTP Host／Origin／Token、nonce CSP、純文字呈現、請求大小與操作鎖、規則循環與去重、JSONL 保存與重啟、來源退避、發送不明、Telegram 保護內容與錯誤遮蔽、啟停腳本及 DACL。
- 全套模擬測試 66 項通過，含新增 5 項；npm 已知依賴漏洞掃描為 0。沒有新增依賴。
- 舊 `src/`、`scripts/` 通知診斷工具僅做危險操作與資料寫入入口搜尋，不視為完成全部 C# 程式審查。本次未重新建置舊工具或重查 .NET 套件。
- 未讀取真實金鑰或登入資料，未啟動真實轉送，也未向 LINE／Telegram 發送訊息。

## 尚未驗證或解決的邊界

- 30 秒期限是停止等待，不代表上游請求已取消；來源未完成時保留同一個請求，需停止並重新啟動才能完全重建連線。LINE 帳號恢復與平台目錄載入仍依賴上游本身的逾時機制；舊單配對模式未套用此新期限。
- 既有磁碟損壞或已寫入的異常紀錄仍採拒絕啟動，不自動修補或丟棄，以免重複發送。
- 未完成朋友電腦、多日壓力、強制斷電、真實跨平台收送、第三方協定與密碼學審查、完整 Git 歷史憑證鑑識。
- 本機憑證仍是 DACL 保護的未加密檔案；同使用者惡意程式不在 HTTP Token 能阻擋的範圍內。
- 沒有完整送達保證。大量積壓、離線、平台保留期限與發送結果不明仍可能漏訊，詳見 [安全說明](../SECURITY.md)。
