# v0.4.0 穩定性優化

日期：2026-10-09。

- 每個來源／目的配對先把篩選後的文字保存並 fsync，再更新讀取進度。重啟恢復尚未發送的內容，來源暫時離線時仍可送出已保存訊息。
- 同目的各來源輪流發送，每輪最多 10 則；同輪發送間隔 1.1 秒，正常輪詢另間隔 3 秒。各配對最多保存 1,000 則待送訊息，滿載後不把尚未入列的訊息標記為已處理。
- Telegram 明確回傳 HTTP 429、錯誤代碼 429 與有效 retry_after 時，保存等待期限；同 Bot 暫停新發送，重啟後仍遵守期限。已在進行中的請求不取消。依據 [Telegram ResponseParameters](https://core.telegram.org/bots/api#responseparameters)。
- 網路中斷、逾時、無回應 ID 與不明錯誤仍阻擋相關配對，不自動重送。
- 待送佇列達 80% 顯示警示；Telegram 收件紀錄達 40,000／50,000 則時預警。
- 規則 API 帶設定摘要，保存時在操作鎖內比對；舊分頁或缺少摘要的請求回覆 409，不覆蓋現有設定。遇到衝突先保留編輯內容，再重新整理頁面。

## 更新與資料

先停止轉送並關閉舊程式，再下載新版。既有 JSONL 可直接讀取；未刪除或重寫舊紀錄，未變更資料庫。第一次使用新版前請自行保留完整資料目錄備份。

新版配對紀錄包含待送的 LINE／Telegram 文字，受既有 Windows DACL 保護但未加密；完成發送後歷史列仍保留。不要分享資料目錄。已入列內容保持入列時的篩選與前綴；之後修改規則不改寫既有待送文字。停用規則只暫停處理，重新啟用會繼續處理待送訊息。

舊版不認得 queued／retry 紀錄，不能把已使用新版的資料目錄直接交給舊版。還原舊備份也可能失去去重進度，勿用降版方式排除發送問題。

## 驗證與限制

模擬測試涵蓋來源離線後重啟恢復、限流期限持久化、容量滿載後補讀、跨輪公平排程、設定衝突與容量預警；不使用真實帳號或發送真實訊息。

實際結果：`npm test` 72／72 通過；`npm audit --omit=dev` 已知依賴漏洞 0；前端 JavaScript 語法與 `git diff --check` 通過。

本次未實作憑證 DPAPI 遷移、日誌封存／磁碟配額、附件、回覆關聯或新通訊平台。日誌與去重集合仍會增長；LINE 1,000 則補讀上限、Telegram 平台更新保存期限仍可能造成漏訊。每輪仍等待來源讀取完成或逾時，尚非完全獨立的來源工作程序。未完成多日運作、真實限流與強制斷電測試。
